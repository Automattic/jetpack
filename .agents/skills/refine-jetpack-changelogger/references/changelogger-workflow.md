# Jetpack Changelogger Workflow

## Repo and command context

- Operate on the current Jetpack checkout (CWD / `git rev-parse --show-toplevel`).
- Prefer `jp` for Jetpack monorepo environment commands.
- Host `git` and `gh` are acceptable for repository inspection, commits, PR metadata, and inline review comments. Prior release work confirmed `gh` was unavailable inside the `jp` environment.
- Do not assume historical changelog entries are in scope. For release review fixes, inspect only the newly generated release block or the commit/PR scope the user named.
- `tools/release-plugin.sh jetpack` also writes the `mu-wpcom-plugin` changelog. During the changelog pause, review both.

## Changelogger generation

- `tools/release-plugin.sh` runs `tools/changelogger-release.sh` during release preparation.
- Changelogger change files live in each project's configured `changelog` directory, defaulting to `changelog/`.
- Prefer improving those change files before generation. That lets changelogger sort the final wording.
- If generated `CHANGELOG.md` files are already present, edit only the latest release block in each touched file unless the user explicitly widens scope.

## Sorting behavior

- `projects/packages/changelogger/src/WriteCommand.php` calls `sortChanges()` (lines 434–452).
- `sortChanges()` delegates to `ChangeEntry::compare()` (`lib/ChangeEntry.php:87-114`) with default ordering `subheading, content`.
- `compareSubheading()` puts empty subheadings first, then known subheadings in configured order, then natural case-insensitive fallback (PHP `strnatcasecmp`).
- Content ordering falls back to natural case-insensitive string comparison.
- **The sort fires at `changelogger write` time, on the wording that existed at that moment.** If you change visible entry text afterward, the generated order may no longer match the final text. The editor's guardrail (see `changelog-style.md § Guardrails`) is to NOT manually reorder mid-wording-pass — instead keep sort fixes and wording fixes in separate commits so the reviewer can verify the wording commit didn't accidentally shuffle anything.

## `Update package dependencies` consolidation source

The verbose multi-line `- Update package dependencies. [#NNNNN]` pattern is generated by `tools/changelogger-release.sh:231-235` and `tools/changelogger-release.sh:244-249`, which auto-append a dep-update entry to every dependent project. The dep-consolidation rule in `changelog-style.md § Update-dependencies consolidation` is cleaning up after this tooling — it's not a contributor pattern.

## Jetpack plugin readme regeneration

Run this after editing `projects/plugins/jetpack/CHANGELOG.md`:

```bash
tools/plugin-changelog-to-readme.sh jetpack
```

The script copies the latest changelog section into `projects/plugins/jetpack/readme.txt`, strips PR numbers, increases heading levels, and omits sections marked as not copied to readme.txt.

The omit mechanism is a literal regex match at `tools/plugin-changelog-to-readme.sh:94` against the HTML comment `<!-- Non-user-facing changes go here. This section will not be copied to readme.txt. -->`. The marker is load-bearing — never edit or remove it while making bullet changes around it, or the `### Other changes` section will start appearing in `readme.txt`.

## Useful local checks

```bash
git diff --check
git diff --name-only -- '**/CHANGELOG.md'
git status --short -- '*/changelog/'
git show --name-only --format=short <commit>
tools/changelogger-validate-all.sh
```

To fetch a PR's inline review comments (across all reviewers):

```bash
gh api repos/Automattic/jetpack/pulls/<PR>/comments \
  --jq '.[] | {user: .user.login, path, line: (.line // .original_line), body}'
```

Append `| select(.user == "<LOGIN>")` to filter to one reviewer. The top-level `gh pr view --json reviews` returns the review summary (often empty body, just `state=COMMENTED`); the inline comment text lives at the `pulls/<PR>/comments` endpoint.

## Hook-failure recipe

Host commits trigger Jetpack pre-commit hooks that require a Node version matching `package.json#engines`. If you hit `ERR_PNPM_UNSUPPORTED_ENGINE`, switch to a matching Node version (`nvm use`, `fnm use`, etc.) and retry the commit.
