# AI Launchpad (Site Setup)

The **Site Setup** wp-admin page (`wp-admin/admin.php?page=site-setup-wp-admin`) that new WordPress.com sites land on: a two-step wizard (goal, then name and description), then a list of six setup tasks picked by AI for that site. It runs on Simple and Atomic. Other teams reuse any part of it (screens, components, endpoints, options, listeners), so this file maps all of it: what each part does, where it lives, and what it assumes.

Code references below name files and symbols, not line numbers. Paths are relative to this directory unless they start with `projects/`.

## How a site gets it

- **Eligibility** is `wpcom_ai_launchpad_is_eligible()` (`eligibility.php`): the `wpcom_ai_launchpad_enabled` option is set **and** `wpcom_launchpad_is_no_guidance()` (`projects/packages/jetpack-mu-wpcom/src/common/launchpad-no-guidance.php`) is false. It is memoized per request, so an option change later in the same request isn't seen.
  - There is no Simple/Atomic check, and `site_intent` is not a gate: it only preselects the wizard goal and feeds a Tracks prop.
  - No-guidance is true when `wpcom_ai_launchpad_no_guidance` is set. Otherwise, while `wpcom_ai_launchpad_enabled` is unset the blog-ID cutoff (`WPCOM_LAUNCHPAD_NO_GUIDANCE_CUTOFF_BLOG_ID`) decides; once it is set, `wpcom_ai_launchpad_dismissed` decides.
  - `wpcom_ai_launchpad_enabled` is written at site creation (outside this repo), by `?enable-ai-launchpad=1`, and by the site-settings endpoint, which can only turn it on.
- **Menu:** "Site Setup" at position 1, above Dashboard, for `manage_options`, hidden once `wpcom_ai_launchpad_completed` is set. The slug is generated by wp-build as `{pageName}-wp-admin` from `package.json` `wpPlugin.pages`, so to rename it, rename the page. The PHP and `build/` must ship together, or the page renders blank.
- **First Dashboard visit** redirects to Site Setup for AI-built sites (`big_sky_site_metadata` has a `siteType`) that have no wizard or AI output yet.
- Calypso's site sidebar is the serialized wp-admin `$menu`, so a change to `admin_menu` here shows up there too.

## How a list gets made

1. `js/app.tsx` loads `GET /wpcom/v2/ai-launchpad` and shows the wizard, or the list if one exists. For AI-built sites it skips the wizard and tailors straight away from the builder's site spec.
2. On finish, the wizard fires `PUT /wizard` without awaiting it, then calls `tailor()` (`js/lib/tailor.ts`):
   - `GET /available-tasks?goal=` returns the ids that can render on this site and goal.
   - `chooseTailoringMenu()` and `buildTailorPrompt()` (`js/lib/prompts.ts`) build an annotated menu and the prompt.
   - The browser calls `jetpack-ai-query` with a Jetpack AI JWT (`js/lib/jwt.ts`; on Simple it uses the site JWT endpoint).
   - It retries once on 429, 5xx, network errors (not its own 40 s timeout), JWT failures, empty content or schema failure, and falls back to `selectFallback()` (`js/lib/fallback.ts`).
3. `commitTailoring()` writes the result with `PUT /tailored`, which validates against `contracts/agent-output-schema.json`, remaps legacy ids, drops unknown and goal-excluded ids, sanitizes subtitles and stores the envelope. On a 4xx it writes the fallback list instead.
4. Every `GET` rebuilds the list on the server (`AI_Launchpad_REST::get_current_tasks()`): the stored AI picks plus read-side overrides, backfilled to six, minus skipped tasks.

The AI never sees or picks an id the site can't render: that is what `available-tasks` and the annotated menu are for. Don't go back to a bare-id menu. With only ids, the model fell back to the handful of self-explanatory ones and every list looked the same.

## Map

### PHP

| File | What it does |
|---|---|
| `ai-launchpad.php` | `AI_Launchpad`: loads everything, the menu, the Dashboard redirect, wp-build loading, initial state (JWT, Tracks, script translations). Loaded from `Jetpack_Mu_Wpcom::load_features()` on every host. |
| `eligibility.php` | `wpcom_ai_launchpad_is_eligible()`. |
| `helpers.php` | Id remaps (`wpcom_ai_launchpad_remap_task_id()`), Tracks props and recorder, site locale and site-language copy, AI-built detection. Every function is wrapped in `function_exists`. |
| `class-ai-launchpad-rest.php` | All REST routes and the server-side list builder (`build_tasks()`, backfill, goal rules, completion latch). |
| `class-ai-launchpad-task-registry.php` | Tasks that exist only for the AI Launchpad (not in the legacy catalog). Filterable. |
| `class-ai-launchpad-listeners.php` | Attaches the legacy catalog's completion listeners to AI-selected tasks. |
| `class-ai-launchpad-*-listener.php` | One completion listener per task family (theme, social, subscribers, subscribe block, About, gallery, contact, events, video, portfolio). The first-post file only registers its marker: the legacy catalog completes `first_post_published` on any publish. |
| `class-ai-launchpad-memberships.php` | Recomputes the payments and paid-plan tasks from local Jetpack Memberships state. |
| `class-ai-launchpad-difm-offer.php`, `class-ai-launchpad-bring-your-ai-tool.php` | ExPlat experiments shown inside Site Setup. |
| `class-ai-launchpad-dev-enable.php` | The `?enable-ai-launchpad` and `?reset-ai-launchpad` query args (see "Working on it"). |
| `contracts/agent-output-schema.json` | The AI output contract, shared by PHP and JS. |

### JS (`js/`, rendered by the wp-build route `projects/packages/jetpack-mu-wpcom/routes/site-setup/`)

| Path | What it does |
|---|---|
| `app.tsx` | Loads the data, decodes entities, seeds Tracks, picks the wizard or the list. |
| `wizard/` | `Wizard`, the goal and details steps, and the experiment views (setup choice, "Which AI do you use?" with MCP connection polling). Pure helpers live in `wizard/lib.ts`. |
| `tailored-list/` | `TailoredList`, `TaskCard`, `Layout`, `SitePreview`, `skeleton`. CTA logic and shared types are in `tailored-list/model.ts`. |
| `difm-offer/` | The "do it for me" banner and its engagement tracking. |
| `lib/` | The tailoring pipeline (`tailor`, `jwt`, `prompts`, `fallback`, `schema-validator`, `commit-tailoring`, `orchestration`, `tailoring-watch`), Tracks, and the page builders below. |

**Page builders** (`lib/first-post.ts`, `about-page.ts`, `gallery-page.ts`, `contact-page.ts`, `events-page.ts`, `video-page.ts`, `portfolio-piece.ts`) create a draft through `wp/v2`, tag it with a marker meta (`_wpcom_ai_launchpad_<task>`), and return a site-relative editor link. For the page builders, the matching PHP listener completes the task when that draft is first published; the first post is completed by the legacy catalog when any post is published. `AI_Launchpad_Markers_Test` keeps the JS and PHP marker keys in sync.

### REST API (`wpcom/v2/ai-launchpad`)

Reads need `edit_posts`, writes need `manage_options`, and both need eligibility. Ineligible sites get a 404.

| Route | Does |
|---|---|
| `GET /` (`?all_tasks=1`) | The whole page state: wizard, tasks, statuses, site info and site-language copy, flags, experiment assignments. May latch completion. |
| `DELETE /` | Dismiss: drops the AI output, the skipped tasks and the completion latch, and sets `wpcom_ai_launchpad_dismissed`. |
| `PUT /wizard` | Stores goal, name, description, locales; also writes `blogname`/`blogdescription`. |
| `GET /available-tasks?goal=` | Renderable and actionable task ids for the tailoring menu. |
| `PUT /tailored` | Stores the AI (or fallback) output. 422 on schema failure, when the last task isn't a launch task, or for a subtitle that is empty or holds a URL or template syntax. The client then saves the fallback instead, so one bad subtitle drops the whole AI list. |
| `POST /complete-task` | Completes a task that has no state to check (`COMPLETE_ON_CLICK_TASK_IDS`). |
| `POST /skip-task` | Adds to `wpcom_ai_launchpad_skipped_tasks`. |
| `GET /mcp-connections`, `POST /mcp-access` | Experiment helpers; need WordPress.com-only functions and degrade without them. |

### Data

- **Options:**
  - `wpcom_ai_launchpad_enabled`, `_no_guidance`, `_dismissed` (autoloaded) and `_completed` (autoloaded latch).
  - `wpcom_ai_launchpad_wizard` and `_ai_output` (not autoloaded; the output envelope holds the AI payload, its source, `ai_built`, `ai_session_id` and `tracked_completed`).
  - `wpcom_ai_launchpad_skipped_tasks`.
  - The shared legacy `launchpad_checklist_tasks_statuses`.
- **Sync:** only the four state flags sync to WordPress.com (`projects/plugins/wpcomsh/feature-plugins/ai-launchpad.php`) and are exposed by the site endpoint and SAL. The wizard and AI output deliberately stay on the site, for size and personal data.
- **Post meta:** one boolean marker per page builder (see above).

### Tasks: where they come from and how they complete

- **The legacy catalog** (`projects/packages/jetpack-mu-wpcom/src/features/launchpad/`) supplies most tasks: `wpcom_launchpad_get_task_definitions()`, visibility, Calypso paths, completion and `wpcom_mark_launchpad_task_complete()`. That last one silently ignores ids it doesn't know, which is why registry tasks write the statuses option themselves.
- **The registry** adds AI-only tasks (`add_gallery_page`, `add_contact_page`, `add_events_page`, `add_video_page`, `add_portfolio_piece`, `add_site_icon`, `pick_fonts_colors`, `install_sensei_lms`). Extend it with the `wpcom_ai_launchpad_task_registry_definitions` filter.
- **Every override lives on the read side, in `build_tasks()`.** The shared catalog is never changed for this feature: id remaps and dedup, `FORCE_VISIBLE_TASK_IDS`, `CTA_OVERRIDES`, the theme showcase CTA, Woo tasks as disabled previews on sell sites without WooCommerce, social tasks hidden on private sites, and launch tasks complete for sites launched at creation.
- **Goal rules** (`GOAL_RESTRICTED_TASK_IDS`, `GOAL_EXCLUDED_TASK_IDS`, `AI_BUILT_EXCLUDED_TASK_IDS`) are enforced when writing and in the menu, not on read.
- **Backfill** tops the list up to six from `backfill_pool()`, cheapest first. `mobile_app_installed` is last because, while it is incomplete, its completion check makes a remote call.
- **Completion signals:**
  - **Calypso can't complete AI-only tasks.** Its completion helper only writes tasks in the site's regular launchpad checklist and does nothing otherwise, so every AI-selected task needs a completion writer in this repo. Calypso writes through the `wpcom/v2/sites/{id}/launchpad` endpoint do reach Atomic. A completion made inside WordPress.com's own code updates only WordPress.com's copy of the site.
  - **Complete-on-click** is for tasks with no state to check, such as profile and share-site. Calypso completes those on view or click too. Don't add a stricter signal than the legacy task has.
  - `setup_ssh` completes optimistically, the way Calypso's SFTP form does: from an Atomic site, the SSH-users endpoint rejects both the blog and user tokens, and the "SSH user created" hook fires on WordPress.com, not on the site.
  - **Subscribers** use `fetch_subscriber_counts()`, because `GET /sites/{id}/subscribers/stats` returns 400 for blog-token requests on Atomic. The raw email count includes the self-subscribed admin.
  - **Memberships tasks** are recomputed live from local Memberships state (the synced connected-account option and the `jp_mem_plan` posts). The catalog callbacks recompute too and return false on Atomic. Being live means deleting a plan un-completes the task.
  - **Domain, Woo and Sensei tasks** complete through their own data (`wpcom_get_site_purchases()`, WooCommerce's tracked-tasks option, Sensei's option). The Woo and Sensei paths were never checked live with the plugins installed.
  - `verify_email` always reads complete where the `Email_Verification` class is missing, which includes Atomic.
- **The fullscreen launchpad stays off.** Listeners skip the legacy "fullscreen launchpad" gate (`wpcom_launchpad_is_task_active_for_completion`) rather than setting `launchpad_screen` to `full`, which would switch on Calypso's legacy `/home` redirect, the My Home card, the mobile-app banner and the editor's post-publish modals. The legacy launchpad forces `launchpad_screen` to `off` for these sites.

### Analytics

- **Tracks:** `jetpack_ai_launchpad_*` events.
  - JS events are fired through `js/lib/tracks.ts`. The server fires `task_completed` (worked out at read time against the `tracked_completed` baseline) and `all_tasks_completed`.
  - Every event carries `wpcom_ai_launchpad_standard_props()`.
  - Booleans are sent as the strings `'true'`/`'false'`, because the PHP and JS clients encode real booleans differently.
  - `is_test` is host-only; `goal` is the AI standard's `site_category` under its own name.
  - On Atomic nothing in wp-admin loads the Tracks transport, so the page enqueues `jp-tracks` itself; without it, `_tkq.push` silently drops events.
- **`ai_session_id`** is minted in the browser, so it exists before the save and survives a failed one.
- **Logstash:** one `tailored` record per tailoring, under feature `atomic_ai_launchpad` (the prefix is required for Atomic's logging endpoint). The wizard's title and description and the inferred `brand_name` are not logged; the other inferred fields (niche, vibe, audience) are. The `wpcom_ai_launchpad_tailoring_log_enabled` filter turns it off.
- **Observing events:** the `wpcom_ai_launchpad_tracks_event` action fires with each server event.

### i18n

- UI strings follow the reader's language; the published copy (drafts, page intros) follows the site's language (`wpcom_ai_launchpad_site_locale()`, `wpcom_ai_launchpad_site_copy()`). The AI gets both and is told which strings use which.
- JS translations load on the server through `wpcom_wp_build_script_translations()` (`projects/packages/jetpack-mu-wpcom/src/common/wp-build-script-translations.php`).
- Under WP-CLI on Atomic, `WPLANG` always reads `en_US`, because wpcomsh hooks `pre_option_WPLANG`. To test site-language behaviour, set the language in the web UI, or with `delete_option( 'WPLANG' )` followed by `add_option( 'WPLANG', … )`.

### Extension points

- **Filters:**
  - `wpcom_ai_launchpad_task_registry_definitions`
  - `wpcom_ai_launchpad_tailoring_log_enabled`
  - `wpcom_ai_launchpad_difm_offer_override_is_treatment`
  - `wpcom_ai_launchpad_bring_your_ai_tool_override_is_treatment`
- **Action:** `wpcom_ai_launchpad_tracks_event`.
- **Pluggable functions:** each `helpers.php` function and `wpcom_ai_launchpad_is_eligible()` can be pre-defined.

## Gotchas

- **The wizard save can race the tailoring.** `PUT /wizard` isn't awaited, so the tailor can land before the goal option exists. `wpcom_ai_launchpad_resolve_goal()` reads the wizard option first and falls back to the payload's goal; keep reads and writes on that one resolver.
- **`blogname`/`blogdescription` are stored HTML-escaped** (`sanitize_option`). Decode them at the API boundary before rendering or re-saving, or they double-escape on each save.
- **`is_plugin_active()` isn't loaded during REST requests**, but some catalog visibility callbacks call it. The REST class loads `wp-admin/includes/plugin.php` first.
- **AI tailoring needs a connected admin.** The JWT endpoint requires a WordPress.com-connected user, so an admin who isn't connected on Atomic gets the fallback list.
- **`add_about_page` always creates a new draft.** Most new sites already have a published placeholder About page, so they end up with two. Adopting the existing page was tried and never landed. Asking the AI for an "edit me" note in drafts blended it into visitor-facing copy.
- **The menu and REST differ on capability:** the menu needs `manage_options`, but REST reads need only `edit_posts`.
- **Some listeners skip the eligibility check.** The page listeners check eligibility. The theme, About, subscribe-block, social and subscriber listeners only check that the AI selected the task.
- **The annotated menu ships on every Site Setup view.** Splitting it into a lazy chunk hasn't been tried, because nobody has checked that dynamic `import()` works under wp-build's import-map loading in wp-admin.

## Working on it

- **Build:** `jp build packages/jetpack-mu-wpcom` (no `--deps` needed for changes here). The route builds to `build/` along with `build/i18n-manifest.json`.
- **Try it on a site:**
  - On WoA, the package ships inside wpcomsh, so sync wpcomsh (see `projects/plugins/wpcomsh/README.md`).
  - As an admin, `?enable-ai-launchpad=1` (`=0` to turn it off) and `?reset-ai-launchpad=1` (clears the wizard, output, dismissed, skipped, completed and task statuses) work on any wp-admin page.
  - `?all_tasks=1` on Site Setup renders every renderable task, for checking cards and CTAs.
  - Any admin can turn the feature on in production; that trade-off was accepted, because there is no reliable Automattician or sticker check on Atomic.
- **Tests:**
  - PHP: `jp test php packages/jetpack-mu-wpcom` (`tests/php/features/ai-launchpad/`).
  - JS: `pnpm test` in the package (`node --test`, the `*.test.mts` files next to the code).
  - Drift tests keep the prompt menu, the catalog and registry, the goal rules, the fallback lists, the marker keys and the inlined schema in sync. Keep them green rather than editing one side.
- **Known gaps:**
  - `routes/site-setup/stage.tsx` is in no tsconfig, so `pnpm run typecheck` skips it.
  - `COMPLETE_ON_CLICK_TASK_IDS` and the theme categories are mirrored in PHP and TS without a drift test.
